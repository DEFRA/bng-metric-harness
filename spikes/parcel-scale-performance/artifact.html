What happens at 5,000 parcels

Baseline GeoPackage validation was measured end to end, from 50 parcels to 10,000, against the real backend code and a real PostGIS. The cost is linear. The development database is not.

2 September 2026 Repos at main · harness 4d5dcf2 Host 2 vCPU · 4 GB · aarch64 PostgreSQL 16 / PostGIS 3.5
01

The answers

A 5,000-parcel baseline GeoPackage takes about 1.6 seconds of server-side work, of which 1.12 s is the PostGIS validation round trip. Add the S3 download of the ~5 MB file and the CDP-uploader wait on top.

The cost is essentially linear in parcel count — roughly 0.19–0.23 ms of database time per parcel from 250 up to 5,000 — turning mildly superlinear only past 5,000 (0.28 ms/parcel at 10,000). There is no cliff and no quadratic blow-up: the GiST-indexed temp table added by BMD-911 already removed the N² behaviour.

Where “noticeable” begins depends on what you measure against.

Nothing in the upload path bounds parcel count. At ~1.05 KB per parcel the 100 MB UPLOAD_MAX_FILE_SIZE_BYTES cap corresponds to roughly 95,000 parcels.

On optimisation: yes, materially. A restructured prototype is 1.8–2.0× faster and makes the separate habitat-sizing round trip almost free. On moving work off the database: no — but move it off the request handler.

02

The environment caveat that changes every number

bng-metric-backend/compose.yml pins postgis/postgis:16-3.5. That tag has no arm64 manifest. On an arm64 host Docker pulls the amd64 image and runs it under QEMU emulation.

$ docker inspect postgis/postgis:16-3.5 --format '{{.Architecture}}'
amd64
$ docker exec bng-metric-backend-postgres-1 uname -m
x86_64          # …on an aarch64 host

The penalty was measured on workloads with no GeoPackage involvement at all, so it cannot be confused with a PostGIS or GEOS version difference:

Emulation penalty · identical queries, two containers, one host
WorkloadEmulatedNativeFactor
count(*) over 20 M rows23,062 ms1,321 ms17×
2 M md5() calls9,058 ms1,283 ms7×
20 k ST_Buffer + ST_Area37.3 ms1.7 ms21×
Consequence

Every local performance observation on an arm64 dev machine is inflated by roughly an order of magnitude. If the perfEvidence figures behind the “System Performance Issues” spike (BMD-869) were gathered on such a machine, they overstate the problem tenfold and should be re-taken.

The fix is one line: pin a multi-arch image. imresamu/postgis:16-3.5 and ghcr.io/baosystems/postgis:16-3.5 both publish arm64, and both were verified against this codebase during the investigation.

Production on CDP runs amd64 natively, so the native column throughout this report is the one that represents production.

The 17.3 MB JSONB project document is not a validation problem, but at 5,000 parcels it is the largest artefact the system creates: 178 ms to insert, 357 ms to jsonb_set, 229 ms just to read back — and it is read by the project list and project summary pages on every visit. At 1,000 parcels it is 3.5 MB; at 10,000 it would be ~35 MB. This is likely to become the binding constraint on large sites before validation does.

04

Where the time actually goes

Each of the fifteen error checks was run in isolation against the same materialised data, sharing the same CTE prefix, so the cost of each rule could be attributed individually. Four things account for essentially all of it — and three of them are structural rather than algorithmic.

Every geometry is parsed and reprojected four times per upload

EXPLAIN (ANALYZE) shows the features_in CTE materialising at ~238 ms native — ST_GeomFromGeoJSON + ST_SetSRID + ST_Transform over all 9,500 features. But the area parcels have already been parsed and reprojected by the statement immediately before it.

PassStatementLayers
1MATERIALISE_AREAS_QUERY · postgis/index.jsareas
2CHECK_QUERY → features_in · postgis/index.jsall six
3CALCULATE_HABITAT_SIZES_QUERY · calculate-habitat-sizes.jsareas, hedgerows, watercourses
4transformToBngMultiGeomSql · persist-upload.jsall, batched 500 at a time

The temp table exists — its comment correctly explains that it gives the GiST index a home — but nothing then reuses it for anything except the overlap join.

Nine megabytes of feature properties are shipped to read three keys

buildArrays sends JSON.stringify(feature.properties) for every feature, and features_in casts all of it with props::jsonb. At 5,000 parcels the parameter payload is 10.9 MB, of which 9.2 MB is properties and only 1.7 MB is geometry — about 1.85 KB of attribute JSON per feature, fully parsed into a JSONB tree on the server.

Everything that payload is used for is this:

COALESCE(props->>'Parcel Ref', props->>'Tree Ref', props->>'Baseline Parcel Ref')
props->>'fid'

Two scalar strings per feature, needed only to name offending features in error messages that fire on a minority of uploads. The other ~1.8 KB per feature — survey dates, company names, base map, comments, condition and significance columns — crosses the wire and is parsed for nothing.

The sliver check dissolves 5,000 parcels to find what the per-parcel check already found

c_slivers_outside computes ST_Union(ST_MakeValid(geom)) over every parcel, then subtracts the red line. In the plan that single Aggregate node is 2,852 ms of the emulated 11,900 ms — the second most expensive node in the statement.

But ST_Difference(⋃Pᵢ, R) and ⋃ ST_Difference(Pᵢ, R) are the same geometry, and c_areas_outside already computes ST_Difference(Pᵢ, R) per parcel one CTE later. On a valid file both are empty. The union of 5,000 polygons is being built to derive something that could be assembled from a rowset that is empty in the healthy case.

The overlap self-join is the one genuinely irreducible cost

At 5,000 parcels the join finds 11,764 candidate pairs — about 2.4 per parcel, the expected count for a planar tiling. The GiST index does its job: candidate generation is 100 ms native. The expense is the confirmation step, ST_Area(ST_Intersection(a, b, 0.001)) > 0.5, which runs a fixed-precision overlay on every one of those pairs — including the ~11,700 that merely share an edge.

The current overlap design is right

ST_Relate, ST_Touches and ST_Overlaps all build the same DE-9IM intersection matrix the overlay itself needs, so substituting one for the other buys nothing. The tolerance-based area test in the current code is both the correct design and close to the cheapest correct one — the comments in postgis/index.js explaining why a Boolean predicate was rejected still hold. gridSize is worth its 14%: dropping it would reintroduce exactly the floating-point ghost slivers it was added to eliminate.

06

A restructured prototype

The changes that did work were assembled into a complete replacement for the two validation statements plus the sizing query. One load statement for every layer, parsing and reprojecting once and repairing once, into a table carrying both raw and repaired geometry plus the two identifier strings — instead of the whole properties blob:

CREATE TEMP TABLE feat_all ON COMMIT DROP AS
SELECT layer, idx, fid, feature_ref, geom, ST_MakeValid(geom) AS geom_valid
FROM (
  SELECT layer, idx, fid, feature_ref,
         ST_Transform(ST_SetSRID(ST_GeomFromGeoJSON(g), srid), 27700) AS geom
  FROM unnest($1::text[], $2::int[], $3::text[], $4::text[], $5::text[], $6::int[])
    AS t(layer, idx, fid, feature_ref, g, srid)
) s;
CREATE INDEX ON feat_all USING gist (geom_valid) WHERE layer = 'areas';
ANALYZE feat_all;

And one escape rowset feeding both parcel-outside errors, gated so that parcels the red line already covers never reach the overlay at all:

c_escapes AS (
  SELECT feat.idx, feat.fid, feat.feature_ref,
         ST_Difference(feat.geom_valid, redl.geom, 0.001) AS escape
  FROM areas feat CROSS JOIN redline_union redl
  WHERE redl.geom IS NOT NULL AND NOT ST_CoveredBy(feat.geom_valid, redl.geom)
),
c_areas_outside   AS (SELECT … FROM c_escapes WHERE ST_Area(escape) > 0.5),
c_slivers_outside AS (SELECT … FROM (SELECT (ST_Dump(ST_Union(escape))).geom … FROM c_escapes) …)

This is a spike, not production code. It has no tests of its own, does not carry the explanatory comments the current module rightly has, and the ST_CoveredBy gates would need their own regression cases for boundary-grazing features before shipping.

One honest wrinkle: the prototype’s overlap check is ~46 ms slower in isolation than the current one, because a partial GiST index over a mixed-layer table is less efficient than the current dedicated areas_g table. Keeping a dedicated area table alongside the shared load table would recover that — a refinement, not a blocker.

07

Should any work move off the database?

No computation should move to Node. PostGIS is doing geometry work in the one place where it is fast, indexed and numerically robust; the JavaScript side accounts for 155 ms of a ~1,600 ms request at 5,000 parcels. Reimplementing overlay or containment in Turf would be slower and would reintroduce the robustness problems the gridSize and tolerance work exists to solve.

Three things should move — but not off the database

  1. Off the request handler. handleReadyUpload calls the backend’s validate endpoint synchronously inside a page request, through a Wreck client with BACKEND_TIMEOUT_MS defaulting to 10,000 ms. The same controller already has a polling loop — REFRESH_INTERVAL_SECONDS = 5, MAX_WAIT_SECONDS = 120 — that it uses while waiting for the CDP uploader. Extending that loop to cover validation removes the 10 s cliff entirely and costs no extra compute.
  2. Into the statement that is already running. Habitat sizing is a separate round trip that re-parses and re-repairs geometry the validation statement has already parsed and repaired. It collapses to ~1% of its cost when read off the loaded table.
  3. Out of the wire. The 9.2 MB of feature properties should never leave Node.

Two considered and not recommended yet

  • Persist geometry first, validate from the table. This would collapse three of the four parse passes into one, but it means writing rows for files about to be rejected — and the current design’s “nothing is persisted” property, stated explicitly at the top of postgis/index.js, is a real one worth keeping.
  • Streaming or chunked validation. Only pays off above ~20,000 parcels, and adds substantial complexity for a case not yet observed.

Throughput flattens at the host’s two vCPUs; beyond that, added concurrency shows up purely as latency. Validation is CPU-bound inside PostgreSQL, so the sizing of the database instance — not the backend task — sets the ceiling.

R2 + R3 + R4 + R5 together are what the prototype measures: 1.8–2.0×. Adding R6 and R7 should reach 2.5–3×, putting a 5,000-parcel file at roughly 400–450 ms of database time and the whole request comfortably under a second.

R1 is first on the list not because it changes production, but because without it the team is optimising against numbers that are ten times wrong.
